# Catalog Schema Reference

**Purpose:** Document the schema and generated artifacts that are present in this repository. Examples below are representative; the checked-in schema is authoritative.

## Status

The schema and aggregate format are **implemented** at:

- `applications/catalog.schema.json`;
- `applications/base/services/<service>/catalog.yaml`;
- `applications/catalog.lock.yaml`;
- `applications/blueprints/<blueprint>.yaml`.

The catalog is metadata. It does not generate deployment manifests.

## Service fragment

```yaml
apiVersion: catalog.opencenter.dev/v1alpha1
kind: ServiceEntry
name: kserve
path: applications/base/services/kserve
packaging: ociHelm
version: v0.18.0
namespace: kserve
source:
  name: kserve
  url: oci://ghcr.io/kserve/charts
components:
  - name: kserve-crd
    kind: crds
blueprints:
  - name: ai-ml
    tier: recommended
requires: [cert-manager, istio]
maturity: beta
renderOwner: none
```

The schema requires `apiVersion`, `kind`, `name`, `path`, and `packaging`. Non-composite entries require `version`; composite entries require `subcomponents`. Helm, OCI Helm, and GitRepository packaging require `source` and `namespace`. Optional fields include `description`, `components`, `deployableAsUnit`, `blueprints`, `requires`, `maturity`, `defaultEnabled`, `renderOwner`, and `versionWaiver`.

`path` is repository-relative and must match the schema's `applications/base/services/...` pattern. The catalog gate also checks that it resolves to a directory.

## Packaging values

The implemented top-level enum is:

| Value | Evidence represented |
| --- | --- |
| `helmRepository` | HelmRelease backed by an HTTPS HelmRepository |
| `ociHelm` | HelmRelease backed by an OCI source |
| `gitRepository` | HelmRelease backed by a Git source/ref |
| `olmSubscription` | Subscription and OperatorGroup resources |
| `remoteKustomize` | Kustomize content using pinned remote manifests |
| `composite` | Parent entry with separately described child paths |

Composite child packaging additionally permits `customResources` in the JSON Schema. `components` describe extra resources in one service directory; `subcomponents` describe separately addressed child paths. Component kinds are `crds`, `storageclass`, and `extra`.

## Blueprint files

Blueprint files contain `apiVersion`, `kind: Blueprint`, `name`, `title`, `description`, and `members`. They may also contain `extends` and `choices`. `hack/scripts/catalog.py` resolves `extends`, checks cycles and member resolution, and incorporates blueprint metadata into the generated lock.

The checked-in files define 11 blueprints, including `minimal`, `enterprise`, `ai-ml`, `observability`, `storage`, `networking`, `security-policy`, `data-messaging`, `cloud-provider-integration`, `hpc-batch`, and `operator-infrastructure`.

## Generated aggregate

`applications/catalog.lock.yaml` is generated by `hack/scripts/catalog.py generate`. The file states that it is generated and should not be edited by hand. The tool orders service entries, resolves blueprint inheritance, and writes the aggregate. `generate --check` and the aggregate gate compare the committed file with generated output.

## Implemented validation

`hack/scripts/catalog.py all` runs:

1. JSON Schema validation;
2. fragment coverage and path resolution;
3. version checks against values filenames, HelmRelease versions, and declared component versions;
4. orphaned Helm-values checks;
5. aggregate freshness;
6. blueprint resolution, membership, and inheritance-cycle checks.

The pre-commit hook runs this command for catalog-related changes. At the current revision, all 47 service directories have fragments, the generated aggregate contains 47 service entries, and the catalog gates pass. These checks validate repository metadata and selected manifest consistency; they do not prove live deployment behavior.

## External renderer boundary

`renderOwner` values describe ownership metadata in the catalog. No openCenter-cli source or catalog reader is present in this repository. CLI convergence, generated Go readers, and deployment behavior are therefore **proposed/external**, not implemented facts here.
