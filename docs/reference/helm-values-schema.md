# Helm Values Schema Reference

**Purpose:** Describes the committed Helm values layout and the override interface exposed to consuming cluster repositories.

**Type:** Reference  
**Audience:** Platform engineers  
**Last Updated:** 2026-09-25

## Base Values Layout

Helm-backed services normally keep their checked-in values under:

```text
applications/base/services/<service-name>/helm-values/
```

The filename follows the upstream version where practical, for example:

```text
values-v1.21.2.yaml
values-1.19.2.yaml
```

The repository also contains service-specific names such as `hardened-values-2.36.5.yaml` and `hardened-values-1.61.3.yaml`. The filename is not itself a schema; the chart determines the supported keys.

## Kustomize Secret Generation

Most Helm service Kustomizations generate a stable base Secret from the checked-in values file. For example, cert-manager uses:

```yaml
secretGenerator:
  - name: cert-manager-values-base
    namespace: cert-manager
    type: Opaque
    files:
      - values.yaml=helm-values/values-v1.21.2.yaml
    options:
      disableNameSuffixHash: true
```

The exact files are service-specific. The observability `kube-prometheus-stack` base Secret currently contains `values.yaml`, `alertmanager-overrides.yaml`, `prometheus-overrides.yaml`, and `alerting-rules-overrides.yaml`.

Some composite or manifest-only services do not expose this pattern. Inspect the service-local `kustomization.yaml` before assuming a generated Secret exists.

## HelmRelease Interface

Helm releases that support consumer overrides reference the generated base Secret first and an optional override Secret second:

```yaml
valuesFrom:
  - kind: Secret
    name: cert-manager-values-base
    valuesKey: values.yaml
  - kind: Secret
    name: cert-manager-values-override
    valuesKey: override.yaml
    optional: true
```

The override Secret is not generated by the base service path. A consuming cluster repository may create it in the HelmRelease namespace. Its name, key, and supported values must match the service manifest and chart. The base repository does not provide a generic `*-values-enterprise` Secret interface.

`kube-prometheus-stack` is a documented exception to the simple two-source example: it reads two additional keys from its base Secret, `alertmanager-overrides.yaml` and `prometheus-overrides.yaml`, before the optional override Secret. The generated `alerting-rules-overrides.yaml` key is not currently referenced by the committed HelmRelease.

## Merge and Ownership

For a HelmRelease with these entries, Helm applies chart defaults, then each `valuesFrom` entry in order. Later values override earlier values according to Helm's map/list merge behavior. This repository owns the base values and the order declared in the committed HelmRelease. Consumers own optional override content and cluster-specific secrets.

Private enterprise values, credentials, ingress names, external endpoints, storage backends, and cluster sizing are not committed as a separate tier in these base service paths. If a private repository supplies them, that is a consumer-owned overlay rather than a repository-wide schema guaranteed here.

## Version Updates

When changing a chart version in a base service:

1. Update the `HelmRelease.spec.chart.spec.version`.
2. Add or update the values file consumed by that service's `secretGenerator`.
3. Update any chart-specific values keys based on the chart's schema.
4. Check the generated Secret keys against `valuesFrom`.
5. Render the service Kustomization and Helm release in the consuming environment.

Do not infer a version from a filename alone. Git-backed and remote-manifest services may use a tag or a Kustomize resource instead of a Helm chart version.

## Common Configuration Surfaces

The following are chart-level conventions, not repository-wide required keys:

- resource requests and limits
- pod and container security contexts
- affinity and tolerations
- persistence and storage classes
- ServiceMonitor or other metrics settings
- ingress or Gateway API integration

Only keys present in a particular chart's values schema should be added to that service's values file. Examples in a consumer overlay must be validated against the selected chart.

## Boundaries and Limitations

- Base values are reusable defaults, not a complete cluster installation profile.
- Override Secrets and their credentials are consumer-owned.
- The base repo does not contain a universal values schema shared by all charts.
- Composite services such as Istio, Kyverno, Keycloak, and observability are assembled from multiple paths and may expose different value interfaces per component.
- A values file can be syntactically valid while still being rejected by the chart; `helm template` or Flux reconciliation is required for chart-level validation.

## Focused Validation

For a Helm-backed service, validate the local Kustomization and then render with the exact chart version and values used by its HelmRelease. For a consumer override, validate the override in the consumer repository because this base repo does not contain that Secret.

```bash
cd applications/base/services/cert-manager
kubectl kustomize .
```

The command checks Kustomize composition only; it does not contact the Helm repository or prove that a chart accepts every values key.
